## Hero video: measured, not yet re-encoded

Measured 2026-08-18 with `ffprobe`, no file changed:

| File | Size | Codec | Resolution | Frame rate | Duration | Bitrate |
| ---- | ---- | ----- | ---------- | ---------- | -------- | ------- |
| `hero-video.mp4` | 28.3 MB | H.264 | 1920×1080 | 60 fps | 61.7s | 3.66 Mbit/s |
| `hero-video.webm` | 24.5 MB | VP9 | 1920×1080 | 60 fps | 61.7s | 3.17 Mbit/s |

Target from the brief was 3–5MB; both files are 5–9× over. Both are video-only
(no audio stream — the hero is `muted` anyway, matching `docs/engineering.md`'s
Performance section). The frame rate is the biggest lever: 60fps buys nothing
for a static background loop and roughly doubles the bitrate a viewer would
otherwise not notice the absence of. Two-pass, targeted at the middle of the
3–5MB range (~4MB) and downsampled to 30fps:

```
ffmpeg -y -i public/video/hero-video.mp4 -vf "fps=30" -an \
  -c:v libx264 -profile:v high -b:v 500k -maxrate 600k -bufsize 1000k \
  -pass 1 -f mp4 /dev/null
ffmpeg -i public/video/hero-video.mp4 -vf "fps=30" -an \
  -c:v libx264 -profile:v high -b:v 500k -maxrate 600k -bufsize 1000k \
  -pass 2 -movflags +faststart public/video/hero-video.optimized.mp4

ffmpeg -y -i public/video/hero-video.webm -vf "fps=30" -an \
  -c:v libvpx-vp9 -b:v 450k -minrate 300k -maxrate 600k \
  -pass 1 -f webm /dev/null
ffmpeg -i public/video/hero-video.webm -vf "fps=30" -an \
  -c:v libvpx-vp9 -b:v 450k -minrate 300k -maxrate 600k \
  -deadline good -cpu-used 2 -pix_fmt yuv420p \
  -pass 2 public/video/hero-video.optimized.webm
```

Not run — re-encoding was explicitly out of scope for this pass. Whoever runs
it should eyeball the result at actual hero size (it's shown small and behind
a scrim, so headroom is larger than the raw numbers suggest) before replacing
the shipped file, and re-run `ffprobe` to confirm the target landed.
